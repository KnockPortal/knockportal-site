## 1. Что это за продукт (бизнес-модель)

KnockPortal — **закрытая** («вещь в себе») система permit-intelligence и адресной связи
домовладельцев с подрядчиками. Публичных каталогов и публичных контактов **нет**.

**Монетизация — только с подрядчиков.** Домовладельцы не платят никогда; они источник интереса и
получатели списка подрядчиков. Это **не маркетплейс** (нет двусторонней монетизации) и **не Angi**
(подрядчик платит не за лотерею проданных лидов, а за присутствие в закрытой рассылке домовладельцам).

**Три актора:**
1. **Подрядчик (contractor)** — платит подписку. Ядро выручки.
2. **Домовладелец (homeowner)** — бесплатно. Оставляет email + категорию интереса, опционально
   описание работы. Получает на email список подрядчиков своей категории.
3. **Оператор (мы)** — закрытая БД, односторонняя рассылка, модерация, юр-контур.

**Несущий принцип закрытости (новое в v1.1):** не только ничего не публикуется на сайте —
**email домовладельца не уходит наружу вообще.** Оператор информирует домовладельца (шлёт ему
список), а контакт с подрядчиком инициирует сам домовладелец. См. раздел 9.0 — это центральное
архитектурное решение, оно определяет схему БД.

### 3.2. Два sticky-CTA — на КАЖДОЙ странице (несущий элемент)

В закреплённой шапке всегда видны **две кнопки**, обе ведут на свой целевой экран:

| CTA | Аудитория | Ведёт на | Стиль |
|---|---|---|---|
| **Subscribe from $99** | Подрядчик (платит) | Pricing + checkout → Stripe | Оранжевая **primary** (единственный оранжевый акцент — бренд-канон) |
| **Submit a request** | Домовладелец (бесплатно) | Request form (категория + email + consent) | **Крупная, контрастная** (slate/strong outline), **равновесная**, НЕ второсортная |

**Двойное назначение «Submit a request» (продуктовое решение, не очевидно — фиксируем):**
Кнопка домовладельца видна не только домовладельцам — **её видит и подрядчик.** Для подрядчика это
**сигнал, что платформа активно привлекает заказчиков** → обоснование, зачем платить $149.
Поэтому она заметная и весомая, а не тихая. Можно усилить микро-подписью рядом: «Homeowners: find a
contractor →».

**Иерархия кнопок:** Subscribe = оранжевая primary (деньги-CTA + единственный оранжевый по канону).
Submit a request = сильная, контрастная, но НЕ оранжевая (оранжевый только один). Обе читаются как
«два важных действия для двух важных аудиторий».

**Честность:** кнопка домовладельца сигналит «тут привечают заказчиков» — это правда (продукт
построен вокруг них). Но тексты для подрядчика **не обещают готовый поток**: «мы активно
привлекаем домовладельцев, поток растёт по мере запуска», а не «у нас тысячи заявок».

## 4. Сценарии (user stories)

**Подрядчик:**
1. С любой страницы жмёт sticky **Subscribe** → `/pricing` или `/contractors` → выбирает тариф →
   платит через Stripe.
2. Stripe webhook автоматически активирует его в Supabase (раздел 8).
3. Заполняет визитку (раздел 5). На $149 — визитка попадает в закрытый каталог + в рассылку.
4. Ежедневно получает permit-registry своей категории/метро на email.

**Домовладелец:**
1. С любой страницы жмёт sticky **Submit a request** → `/request` → выбирает категорию → оставляет
   email → **ставит consent-галочку** → опц. описание работы.
2. Получает **письмо-подтверждение** (double opt-in, раздел 10) → подтверждает клик.
3. После подтверждения получает на email **список из 3 подрядчиков** своей категории (подвыборкой,
   6.1; если пусто — честный fallback).
4. **Дальше домовладелец сам** связывается с выбранным подрядчиком. Оператор в контакте не
   участвует, email домовладельца наружу не уходит.

## 5. Визитка подрядчика (поля)

Принцип: **минимум обязательного + максимум свободы.**

**Обязательный минимум (без него визитка нерабочая):**
- Название компании / имя
- Категория(и) работ (сквозной справочник, раздел 6) — ≥1
- Метро / зоны обслуживания — ≥1
- Контакт для домовладельца (email и/или телефон) — ≥1
  *(этот контакт подрядчика показывается домовладельцу в визитке — домовладелец сам по нему пишет.
  Это контакт ПОДРЯДЧИКА, который он осознанно публикует в своей визитке, не контакт домовладельца.)*

**Опциональные поля (свобода подрядчика):**
- Подробное описание (свободная форма), лицензия/номер, годы опыта, сайт, соцсети (ссылки),
  фото (логотип, фото работ), любые доп. сведения.

> Подрядчик сам решает глубину заполнения. Мы не отвечаем за достоверность (фиксируется в ToS).
> Но **базовая модерация** (не мат, не фейк, не чужой бренд) — перед попаданием в рассылку.

## 6. Категории работ — сквозной справочник

**Решение: единый сквозной справочник категорий для ВСЕХ метро/штатов** (не per-metro). Связь с
метро — many-to-many. Упрощает БД и рост.

**Источник:** нормализация типов работ из реальных permit-описаний (уже выкачаны): re-roof,
roof-repair, hvac-changeout, electrical/panel-upgrade, solar, waterproofing, и т.д.

**Phase 0:** живая категория — **roofing (re-roof)** по SF-данным. Остальные **заводятся в
справочник заранее** (структура сквозная), наполняются позже.

**Задача для данных:** выделить чистый список категорий из permit-фида → нормализовать → засеять
таблицу `categories`. Вход для БД-схемы.

### 6.1. Подбор «3 подрядчика» — подвыборка, ротация, matching-logic

Домовладельцу шлётся **не весь список мемберов категории, а подвыборка** (по умолчанию 3).

**Зачем подвыборка (анти-парсинг):** конкурент может притвориться домовладельцем и фармить заявки,
чтобы спарсить список платящих мемберов. Защита:
- Отдавать **3 подрядчика, не весь список** — одна заявка не вскрывает базу.
- **Ротация/рандомизация** — разным «домовладельцам» в одной категории разные подвыборки, чтобы
  агрегацией нельзя было собрать полный список.
- **Анти-абуз:** rate-limit на заявки с email/IP; double opt-in (раздел 10) ломает массовый фарм
  (нужно подтвердить каждый email).

**Matching-logic (реальная, не декоративная):** подбор = категория + метро + ранжирование
(полнота визитки / давность / ротация). Это **настоящая логика**, поэтому маркетинг может честно
говорить **«smart match» / «подобрано под ваш запрос»**.

> ⚠️ **AI-washing — осторожно (под юр-ревью).** Называть это «уникальный ИИ-алгоритм» при отсутствии
> реальной ML-модели — потенциально вводящее в заблуждение (FTC в US бьёт по фейковым «AI-powered»
> заявлениям). Решение: пока в системе детерминированная matching-logic → маркетинг = «smart match»,
> «algorithmic matching». Слово **«AI» приберечь** до момента, когда там реально будет модель.
> Финальная формулировка — юрист.

## 7. База данных (Supabase) — схема

Спроектировать **один раз, на рост**. Сквозная структура. Каркас (не финальный DDL):

```
categories
  id (pk), slug, name, description, active(bool), created_at

metros
  id (pk), slug, name, state, active(bool), data_source(text), created_at

category_metros            -- many-to-many: какие категории живы в каком метро
  category_id (fk), metro_id (fk)

contractors
  id (pk), auth_user_id(fk→supabase auth), company_name, contact_email,
  contact_phone(nullable), description(text), license(nullable), years(nullable),
  website(nullable), socials(jsonb), status(enum: pending/active/suspended),
  plan(enum: registry / registry_presence), stripe_customer_id, stripe_subscription_id,
  created_at, updated_at
  -- contact_email/phone здесь = контакт ПОДРЯДЧИКА для его визитки (он сам публикует)

contractor_categories      -- many-to-many: подрядчик ↔ категории
  contractor_id (fk), category_id (fk)

contractor_metros          -- many-to-many: подрядчик ↔ зоны/метро
  contractor_id (fk), metro_id (fk)

contractor_media           -- фото/логотипы
  id (pk), contractor_id (fk), url, kind(enum: logo/photo), sort_order

homeowner_leads            -- интересы/заявки домовладельцев. EMAIL НЕ УХОДИТ НАРУЖУ.
  id (pk), email (ШИФРОВАНИЕ at-rest, RLS, НИКОГДА public-read, НИКОГДА не передаётся),
  category_id (fk), metro_id (fk, nullable), request_text(nullable),
  consent(bool, NOT NULL), consent_ts(timestamp), ip(text, аудит consent),
  confirmed(bool, default false),       -- double opt-in: подтверждён ли email
  confirm_token(text), confirm_ts(timestamp, nullable),
  status(enum: pending_confirm/confirmed/dispatched/closed), created_at

homeowner_dispatches       -- лог: какому домовладельцу какой НАБОР ВИЗИТОК отправлен
  id (pk), lead_id (fk), contractor_ids(jsonb -- какие 3 визитки вошли в подвыборку),
  sent_at, is_duplicate(bool -- дубль через неделю или первичная)
  -- ЭТО НЕ передача контакта. Это аудит односторонней отправки списка домовладельцу.

subscriptions              -- зеркало Stripe для быстрых проверок доступа
  id (pk), contractor_id (fk), stripe_subscription_id, plan, status,
  current_period_end, created_at, updated_at

registry_deliveries        -- лог доставки permit-реестра подрядчику
  id (pk), contractor_id (fk), category_id, metro_id, sent_at, permit_count

permits                    -- кэш выкачанных permits (опц., если храним у себя)
  id (pk), source_id, metro_id, category_id, address_full, address_masked,
  cost, issued_date, status, raw(jsonb), created_at
```

**Ключевое отличие v1.1:** нет таблицы «передачи контакта подрядчику». `homeowner_dispatches`
логирует только **одностороннюю отправку списка визиток домовладельцу** (какие 3 вошли, когда,
дубль или нет). Email домовладельца **остаётся в `homeowner_leads` под RLS + шифрованием и наружу
не уходит**.

**Ключевые связи:** подрядчик ↔ категории ↔ метро (many-to-many через сквозной справочник);
заявка homeowner привязана к категории+метро → подвыборка подрядчиков по этим связям (6.1).

**RLS (Row Level Security):** обязательно везде. Подрядчик видит только свои данные.
`homeowner_leads` и `contractors` — **никаких public-read политик**. `homeowner_leads.email` —
шифрование at-rest, доступ только серверной роли оператора для рассылки.

## 8. Stripe ↔ Supabase (активация подрядчика) — Phase 0 автомат

**Решение: webhook-автоматизация уже на Phase 0** (пользователь подтвердил — несложно).

Поток:
1. Подрядчик платит через Stripe Payment Link ($99 или $149).
2. **Stripe webhook** (`checkout.session.completed` / `customer.subscription.created`) →
   серверный endpoint (Supabase Edge Function или Vercel API route).
3. Endpoint создаёт/активирует `contractors` + `subscriptions`, ставит `status=active`, `plan` по
   цене, сохраняет `stripe_customer_id` / `stripe_subscription_id`.
4. Подрядчик получает письмо-приглашение завершить регистрацию (заполнить визитку) — magic link
   через Supabase Auth на email из Stripe.

**Webhook-безопасность:** проверять подпись Stripe (`stripe-signature`), идемпотентность по
event id. `sk_live` — ТОЛЬКО на сервере (env var), никогда на фронте.

**Отмена/неоплата:** `customer.subscription.deleted` / `invoice.payment_failed` →
`status=suspended`, визитка выпадает из рассылки.

## 9. Юридический контур — ОБЯЗАТЕЛЬНО (под ревью юриста)

> Закрытость снимает риски **публикации**, но НЕ отменяет правила **обработки персональных данных**.
> Ты собираешь email домовладельцев. В Модели B2 (ниже) ты их **не передаёшь** — это резко снижает
> нагрузку, но не обнуляет её (хранение, рассылка, право на удаление остаются). Каждый текст ниже —
> под юр-ревью (пользователь анализирует «каждое слово» — правильно).

### 9.0. Несущее решение: email домовладельца НЕ передаётся НИКОМУ (Модель B2)

**Это центр архитектуры. Зафиксировано пользователем «раз и навсегда».**

- Email/контакт домовладельца **НЕ передаётся подрядчикам или кому-либо — ни при каких условиях.**
- Оператор хранит email под безопасным протоколом (RLS + шифрование at-rest) и использует его
  **исключительно для односторонней отправки домовладельцу** списка подрядчиков его категории.
- **Контакт инициирует домовладелец сам** — он получает визитки (с контактами подрядчиков, которые
  те осознанно опубликовали) и сам пишет выбранному.
- Оператор — **чистый информатор-посредник**, а не «передающий контролёр ПД». Это юридически
  гораздо чище модели с передачей контакта.

> **Слепое пятно (осознанный размен приватность ↔ измеримость):** раз контакт домовладельца не
> уходит, а он сам пишет подрядчику, оператор **не видит** воронку на стороне домовладельца (написал
> ли, заключил ли сделку). Сигнал, что механика работает, приходит косвенно — через retention
> подрядчиков ($149 продлевают = им идут домовладельцы). Это by design, не дефект.

### 9.1. Consent домовладельца (смягчён в v1.1)

Форма ОБЯЗАНА содержать явный чекбокс (не пред-отмеченный). Поскольку передачи контакта НЕТ,
формулировка проще:
> «Я согласен(на) получать на указанный email список подрядчиков по выбранной категории работ.»
> (финальная формулировка — юрист)

Хранить `consent=true`, `consent_ts`, `ip`. Плюс double opt-in (`confirmed`, `confirm_ts`) как
второй слой подтверждения (раздел 10). Без consent + подтверждения — рассылка не идёт.

### 9.2. Privacy Policy (`/privacy`)

Что собираем (email, категория, опц. описание; для подрядчиков — визитка), зачем, **что email
домовладельца не передаётся третьим лицам**, сроки хранения, право на удаление. Оператор —
Abalon LLC, адрес Raleigh.

### 9.3. Terms of Service (`/terms`)

- Информационный сервис, **не гарантируем** качество/исход работ подрядчиков.
- Достоверность визитки — ответственность подрядчика.
- Способ контакта с домовладельцем — ответственность подрядчика (но контакт инициирует домовладелец).
- Disclaimer «сервис в развитии».

### 9.4. CAN-SPAM (письма домовладельцам и визиточный поток)

Каждое письмо домовладельцу: физ-адрес отправителя (Abalon, 4030 Wake Forest Rd Ste 349, Raleigh
NC 27609), рабочий unsubscribe, честная тема. Реестр платящему — транзакционка, но гигиену

### 9.5. TCPA / телефон

### 9.6. Disclaimer «в развитии» (честность)

шлётся по мере появления мемберов. Не обещать поток, которого нет.

## 10. Почтовая архитектура (несущий раздел — переписан в v1.1)

**У продукта ТРИ разных потока почты. Их нельзя смешивать** — иначе репутация домена сгорит и
платящие подрядчики перестанут получать реестр.

| # | Поток | Природа | Домен/контур |
|---|---|---|---|
| 1 | **Реестр подрядчику** (ежедневный permit-дайджест платящему) | Транзакционка (заплатил, ждёт) | Транзакционный субдомен |
| 2 | **Список визиток домовладельцу** (3 подрядчика по подтверждённой заявке) | Солиситед (сам попросил), но коммерческий контент | Транзакционный субдомен (тот же) |
| 3 | **Холодный аутрич подрядчикам** (привлечение) | Холодная почта | **Отдельные домены, прогрев, строго врозь** |

### 10.1. Контуры доменов

- **Корневой `knockportal.com`** — official-почта (Zoho, `hello@`/`team@`), Stripe, бренд.
  **Не рассылает** — репутация чистая.
- **Транзакционный субдомен** (напр. `send.knockportal.com`), через **Resend** — несёт **потоки 1
  и 2** (оба солиситед, оба адресата ждут письмо → общая здоровая репутация).
- **Отдельные домены** — поток 3 (холодный аутрич), прогрев 2–3 недели, **никогда** не касается
  `knockportal.com` и его субдоменов (репутационный карантин — как в network-stack).

**Зачем субдомен, а не голый домен:** если доставка просядет — страдает субдомен, а корневой домен
(Stripe, official, бренд) остаётся чистым. Изоляция репутации.

**Раздельные From на одном субдомене (страховка на будущее, опц.):**
`registry@send.knockportal.com` (реестр) и `match@send.knockportal.com` (визитки домовладельцу) —
чтобы при росте жалоб на коммерческий поток 2 видеть его отдельно и изолировать, не утянув реестр.
Не третий субдомен — тот же `send.`, разные отправители.

### 10.2. Double opt-in для домовладельца (killer-приём — решает 4 проблемы разом)

После заявки первым письмом — **подтверждение**, не визитки: «Подтвердите, что хотите получить
подрядчиков по [категория] — нажмите кнопку». Только после клика — высылается список из 3 визиток.

Закрывает разом:
- **Доставляемость:** первое письмо — чистая транзакционка (подтверждение), идеально доставляется,
  прогревает связь; визитки идут уже вовлечённому адресу.
- **Анти-парсинг** (защита мемберов): конкурент-фармер должен подтвердить каждый email → массовый
  фарм ломается.
- **Consent-аудит** (юр): клик-подтверждение с таймстампом = железное доказательство согласия.
- **Чистота базы:** фейк/мёртвые адреса отсеиваются, баунсы не копятся → репутация отправителя цела.

### 10.3. Технический минимум

- **Сервис: Resend, бесплатный тариф** (3,000 писем/мес, 100/день — для Phase 0 с запасом).
  Фит со стеком: React Email = шаблоны как JSX-компоненты в Next.js. Платить $0 на старте.
  Альтернатива при критичности доставки позже — Postmark (дороже, но топ по inbox-placement).
- **SPF / DKIM / DMARC на субдомене — ОБЯЗАТЕЛЬНО.** Resend даёт DNS-инструкции при добавлении
  домена. Без них Gmail/Yahoo (ужесточение 2024+) режут в спам. Не опционально.
- **CAN-SPAM в потоке 2:** физ-адрес + unsubscribe + честная тема (раздел 9.4).
- **Письмо-список (поток 2):** 3 визитки подрядчиков (подвыборка, 6.1). Формат — HTML-шаблон
  (React Email), бренд-канон. Контакты в визитках — это контакты ПОДРЯДЧИКОВ (они опубликовали).

### 10.4. Локальные адреса под метро (доверие, roadmap)

Схема — **НЕ** `knockportal.sf.com` (sf.com чужой). Старт: `sf@knockportal.com` (просто).
Субдомены под метро (`sf.knockportal.com`) / отдельные домены — roadmap, когда оправдается.

## 13. Фазировка

**Phase 0 (валидация — критично для go/no-go):**
- Сайт: 5 контентных страниц + sticky-шапка с 2 CTA; целевые экраны (Pricing/checkout, For
  contractors, Request form); Legal (Terms, Privacy).
- Подрядчик: оплата ($99/$149) → Stripe webhook → Supabase активация → заполнение визитки.
- Домовладелец: форма (категория + email + consent) → double opt-in → запись в БД.
  **Сбор есть; активная рассылка визиток — по готовности (см. ниже).**
- Permit-registry: SF, roofing, ежедневная email-доставка (cron на VPS: sf_pull + sf_clean).
- Категории: сквозной справочник засеян; живая — roofing SF.
- Почта: транзакционный субдомен + Resend + SPF/DKIM/DMARC + double opt-in.
- **Критерий go: ≥3 оплаты ИЛИ ≥10 явных намерений за 2 недели, стоп-лосс <$600.**

**Phase 1 (после сигналов PMF):**
- Полноценная активная рассылка визиток домовладельцам по категориям + ротация.
- Owner-обогащение (SF assessor) как возможный $199-слой.
- Доп. метро/категории, локальные субдомены/почты, прогрев под масштаб.
- (Возможно) реальная ML-модель подбора → тогда честно «AI matching».

> Рассылка визиток домовладельцу **спроектирована в БД сейчас**, но активируется, когда есть
> критическая масса подрядчиков-мемберов в категории. До этого — честный fallback домовладельцу.
> Решающий критерий go проверяется **подрядной стороной** (платят ли за permits + присутствие).
